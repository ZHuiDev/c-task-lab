# 完整项目源码导读

## 模块如何合作

```text
键盘 → input_line → input_ulong/标题验证 → main 中的菜单
                                      ↓
                                task_* 管理内存
                                      ↓
                                  TaskList → task_save/task_write → 磁盘

磁盘 → task_load/task_read → 临时 TaskList → 全部成功后替换当前 TaskList
```

读文件时先把磁盘内容转换成临时列表；全部成功才交给菜单。

| 文件 | 职责 | 先找这些问题 |

| `src/task.c` | 增删、查找、位标志、扩容与排序 | `len` 和 `cap` 有何区别？为什么 `realloc` 不直接写回原指针？ |
| `include/input.h` / `src/input.c` | 整行输入和严格数字解析 | `fgetc` 为什么用 `int`？长输入之后，下一次读取从哪里开始？ |

## 把“添加任务”追到最底下

1. 菜单读入一整行数字，经 `input_ulong` 变成合法菜单值。字符串 `"2x"` 不会被当作 `2`。
2. 读标题和优先级，调用 `task_add(&list, title, priority, &id)`。
3. `task_add` 检查参数。标题必须含有终止符，长度 1–95 字节，且没有 ASCII 控制字符；不检查 Unicode 编码是否有效。
4. 把标题先复制到局部 `Task`。即使传入的是旧任务的标题，后面的扩容也不会让复制源失效。
5. 若 `len == cap`，检查大小计算，再用临时指针接收 `realloc`。失败时仍保留旧表。
6. 把新任务写到 `items[len]`，增加 `len` 和 `next_id`，通过输出参数交还编号。
7. 菜单把 `changed` 设为真。内存已变更，磁盘要等菜单 7 才更新。

动手：设置断点，观察第一次添加前后的 `items`、`len`、`cap`、`next_id`；再连续添加超过 8 项，观察容量变化。调试器使用方法见课程的调试章节。

## 内存与指针

```text
main 的局部 list
  items ───→ 动态分配的 Task 数组：[任务1][任务2]...[空位]
  len = 2                  有效下标 0..len-1
  cap = 8                  总容量，空位不是有效任务
  next_id = 3              业务编号，不是数组下标
```

`task_free(&list)` 释放数组。`task_find` 返回的指针借用数组中的一项，调用者不能释放它。扩容可能移动数组；删除会移动元素；排序会调换元素。发生这些操作后，即使地址还没变，也应按 ID 重新查找，不把旧指针当作原来的任务。

`const Task *` 限制经这条指针修改任务，不表示整个程序中任务永远不会改变。`void *context` 是回调额外携带的信息；本项目传 `stdout`，让回调知道往哪里打印。回调不可以在遍历期间增删、排序或释放原列表。

## 文件为什么这样设计

例子（这里的列用真正的制表符分隔）：

```text
CTASK	1	4
1	3	1	Learn C
3	2	0	Draw memory
```

上面展示的是可见的 `\t` 转义；实际文件必须使用 TAB 字符。头分别是标识、版本、下一个任务 ID；记录分别是 ID、优先级、标志、标题。每行包括最后一条都要换行，输入可为 LF 或 CRLF。删除任务 2 后，`next_id` 仍为 4，重新读取也不会把删除过的最大编号再次使用。

读取时会拒绝：错误版本、缺字段、多字段、空标题、控制字符、重复 ID、未知标志、负数字符串、超范围数字、不合法的下一个 ID、超长行、嵌入 NUL 和未换行的截断记录。先读入临时列表，所有检查通过才替换旧表。文件关闭失败也会使路径读取失败，旧表保留。

文本避免了结构体填充、字节序和整数宽度带来的原始内存格式问题，但仍有平台范围限制：例如 Windows 的 `unsigned long` 通常比 64 位 Linux 窄，跨平台文件中的 ID 必须在接收方范围内。它也不提供数据库事务、并发锁或断电保护。

保存用 `fopen(path, "wb")` 直接覆盖，并检查写入与关闭错误。写到一半失败可能损坏原文件。不要用重要数据练习。下一步可设计临时文件写入与替换；要查目标系统的重命名与持久化保证，ISO C 本身不保证跨平台的原子替换或断电安全。

## 复杂度与取舍

- 按 ID 查找、删除最坏都需要线性扫描，`O(n)`；删除还可能移动后面的元素。
- 容量成倍增长可让一般情况下的追加获得摊销常数级扩容开销；单次扩容仍可能搬移整个数组。
- 排序使用标准库 `qsort`，C 标准不承诺它的具体算法、稳定性或复杂度；不要根据名字就认定它一定是快速排序。本项目用“优先级降序，ID 升序”确定并列次序。
- 文件读取检测重复 ID 和保存前的完整性检查采用嵌套/重复线性查找，最坏 `O(n²)`。适合教学小数据；大量记录应考虑索引与哈希集合。

## 五个毕业挑战

先自己实现，再运行 `-Action test`，并针对新增行为补最小必要检查。

| 挑战 | 完成标准 | 会用到的知识 |
|---|---|---|
| 按标题片段搜索 | 搜索 `C` 可显示匹配任务，空查询有明确定义；不越界 | 字符串、遍历、`strstr` |
| 只显示待办 | 不删除数据，统计仍能区分全部与待办 | 位运算、条件、回调 |
| 改名 | ID 不变；空、超长、控制字符标题被拒绝；失败保留旧名 | 接口设计、验证、字符串复制 |
| 安全保存策略 | 写临时文件失败时保留旧文件；写完后有明确的替换策略 | 错误处理、文件生命周期、平台边界 |
| 给任务增加截止日期 | 明确日期格式、合法日期与文件版本迁移规则 | 结构体、解析、`time.h`、数据格式演进 |

验收不是“能启动”：演示一次正常情况、一次边界情况、一次失败情况，并说明内存和文件在每一步的状态。若想继续并发、网络、嵌入式或系统编程，先完成 [ROADMAP.md](ROADMAP.md) 中的核心验收，再选择一个方向。
